# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

# ctnlist mailing list

ctnlist (v6.0.4) is a web-based mailing-list application. v5.0 is the **behavioural baseline**: changes should preserve established v5 workflows rather than redesign them. See `README.md` and `RESTORED-FUNCTIONALITY.md` for the full feature and invariant list.

## Development software

- PHP v8.5.11 (`composer.json` declares `>=8.4.1 <9.0`, platform pinned to 8.4.1, the Symfony 8.1 minimum)
- PostgreSQL v16.15
- Symfony 8.1 (framework-bundle 8.1.8, runtime, dotenv, twig-bundle, security-bundle, security-csrf, mailer, asset-mapper, form, validator, http-client, html-sanitizer, rate-limiter) with Doctrine DBAL 4 / DoctrineBundle 3 (no ORM)
- Frontend: Bootstrap 5.3 and Bootstrap Icons from jsDelivr (with SRI), application CSS/JS through AssetMapper, CKEditor 5 on the editor pages; no Node/npm, no jQuery
- Other dependencies: Phinx (migrations); PHP `gd` (JPEG, WebP) and `exif` for profile pictures; PHPStan and PHPUnit for dev

## Local development environment (podman)

`bin/dev` drives a podman-compose stack (`compose.yaml`, files in `dev/podman/`): nginx 1.30 → PHP 8.5-FPM, PostgreSQL 16 and Mailpit. Containers mirror the production layout (repo mounted at the shared-code path `/usr/local/lib/php/ctnlist/6.0.4`, the repo's `public_html/` mounted read-only at `/var/www/ctnlist/public_html`, `.env` one level up, writable `var/` volume).

```bash
bin/dev up                  # build, start, composer install (first run), clear the instance cache, run migrations (also ctnlist_test, ctnlist_banlist_test), seed admin@ctnlist.test
bin/dev seed-admin [email]  # create/promote another administrator
bin/dev console <args>      # bin/console as www-data for the dev installation (e.g. bin/dev console debug:router)
bin/dev help                # all commands: down, restart, ps, logs (follows; never pipe it), migrate, status, check, psql, shell, composer, php, ensure-env, cattomail-link, cattomail-status, cattomail-ca, test-cattomail, reset-db
```

- App http://localhost:8180 (and https://localhost:8543 with a development certificate generated by `bin/dev up` into `dev/podman/tls/`, gitignored), Mailpit http://localhost:8125 (transactional mail is captured there; log in via the magic link it receives), PostgreSQL `localhost:5434` (ctnlist/ctnlist).
- Campaign content goes to catto-mail, which the dev stack does not configure by default: the queue, proofs and resends then report "catto-mail is not configured" and keep their work. Connecting the local catto-mail is the README's "catto-mail development route" (`bin/dev cattomail-link` attaches web/app to the internal `cattomail-dev` network, and `bin/dev up` re-attaches them automatically whenever that network exists (it never creates it or fails without it); `bin/dev cattomail-status` lists what the route has and lacks without printing secrets; `bin/dev cattomail-ca` pins catto-mail's development certificate; catto-mail's own side is configured in its repository, never from here). `bin/dev test-cattomail` is the optional real end-to-end check (`ctnlist:cattomail:check --e2e`: one proof and one validation job, only in dev/test against a local catto-mail); it is never part of `bin/dev test`.
- First `bin/dev up` generates `dev/podman/ctnlist.env` (gitignored) from `ctnlist.env.dist` with random `APP_SECRET`/`APP_INSTANCE_ID`/`APP_SETTINGS_KEY` (`bin/dev ensure-env`, run by `up` before the containers start: an existing file is kept, and only a missing or empty `APP_SETTINGS_KEY` is filled in, in place so a running bind mount sees it; an existing key is never replaced, since stored secrets depend on it; `tests/Unit/DevEnvironmentTest`). Never commit generated secrets or use placeholder values.
- The dev stack has no banlist database: it runs with `SUPPRESSION_PROVIDER=none`, which is only accepted when `APP_ENV` is `dev` or `test` (`SuppressionCheckerFactory`). The banlist (ctnlist's own shared suppression database) is separate from catto-mail's global transport suppression; ctnlist never queries catto-mail's suppressions.
- Run PHP tooling inside the container (`bin/dev composer …`, `bin/dev analyse`); there is no host PHP.
- `bin/dev reset-db` deletes the `ctnlist_pgdata` volume and re-runs `up`. It prompts for the word `reset`, so a non-interactive run needs `echo reset | bin/dev reset-db`.

## Commands

`vendor/` is not committed; `bin/dev up` runs `composer install` on first start. In dev, run these through `bin/dev` (e.g. `bin/dev composer migrate-paralegal`).

```bash
bin/dev check                        # THE quality gate (run before handing work back): lint, lint:twig --show-deprecations, lint:yaml, lint:container, composer validate --strict + audit, PHPStan, all tests; stops at the first failure
bin/dev analyse                      # composer analyse: PHPStan level 8 over src/, public_html/index.php and tests/ (phpstan.neon; no baseline, no ignores)
bin/dev lint                         # php -l over public_html/index.php, src/ and tests/ (how the tree is validated during packaging)
bin/dev test                         # PHPUnit (phpunit.dist.xml): suites unit, integration, smoke (--testsuite unit,integration skips HTTP)
bin/dev test --filter <TestName>     # single test or data-set, e.g. --filter 'testRouteRendersForAdministrator@/lists'

composer migrate-paralegal  # main DB migrations (database/migrations/domain)  = bin/dev migrate
composer status-paralegal   #                                                 = bin/dev status
composer migrate-banlist    # global suppression DB migrations (database/migrations/banlist); not used in dev
composer status-banlist
```

Tests: `tests/Unit` (plain PHPUnit), `tests/Integration` and `tests/Smoke`.
- Integration tests extend `IntegrationTestCase`: the kernel in the `test` env against the `ctnlist_test` database, each test inside a rolled-back transaction (create any rows you need; fixture helpers `createSubscriber()`, `createList()`, `setMembership()`, `createMessage()`), mail on the null transport with Symfony's mailer assertions. Env comes from `phpunit.dist.xml` (SUPPRESSION_PROVIDER=none, MAILER_DSN=null://null, …). In the test env every `App\` service is kept public (`Kernel::build()`) so tests can fetch services nothing uses yet. `tests/bootstrap.php` recompiles the test container on every run (APP_DEBUG=0 would keep a stale one). The banlist checker is tested against `ctnlist_banlist_test` (`dev/podman/banlist-test.env`). Tests run as root in the container; `bin/dev test` first makes `var/cache` www-data-owned so PHP-FPM can still build its cache.
- Smoke tests: HTTP against the running stack; base class `SmokeTestCase` provides `client()`, `request()`, `issueLoginToken()`, `loginAsAdmin()`, and for Symfony forms `formFields()` (what a browser submits for a form on a page), `submitForm()` (load a page, submit one of its forms with overrides, e.g. `['list[name]' => 'x']`) and `submitAndFollow()` (expects the post/redirect/get success and returns the next page, or fails with the form's errors); `csrfToken()` reads any token on a page. `AuthFlowTest` covers magic links, auth cookies, logout and CSRF; `LayoutTest` the shared layout (assets, sticky header, anonymous/subscriber/administrator/custom-role navigation, CKEditor only on editor pages, error pages; fixture `smoke-nav@ctnlist.test`); `AdminScreensTest` the administration screens (page headers, confirmations, pagination markup, permission-aware actions; fixture `smoke-staff@ctnlist.test`); `RoleAdministrationTest` roles end to end and proofs to any address (fixtures `smoke-roles@`, `smoke-member@ctnlist.test`); `SettingsPageTest` the Settings page (it restores any existing overrides afterwards; the running stack needs `APP_SETTINGS_KEY` in `dev/podman/ctnlist.env`, which `bin/dev up` adds). Fixture cleanup must delete only the test's own roles: never remove a subscriber's system `subscriber` role; `AdminListsRolesTest` list/role administration and ACL; `AdminMessagesTemplatesTest`, `AdminQueueTest`, `AdminSubscribersTest` and `ReportsTest` the rest of the administration and the Site Log; `CattoMailSmokeTest` the catto-mail pages and webhook endpoint on the unconfigured dev stack; `ProfileTest`, `ConsentTest`, `MessageActionTest`, `ArchiveContactTest` the subscriber pages (persistent fixture subscribers: `smoke-editor@`, `smoke-forward@ctnlist.test`). `list_subscription_events` is append-only (trigger), so subscribers with consent events can never be deleted: tests must reuse persistent fixture subscribers (e.g. `smoke-editor@ctnlist.test`) rather than create and delete them. `tests/Smoke/RouteSmokeTest` requests every GET route of the running stack over HTTP (from the app container to `http://web`), anonymously and as `admin@ctnlist.test` (logged in by inserting a magic-link token). It creates and deletes its own message/template/archive/catto-mail fixtures in the dev DB. Add every new GET route to it: `tests/Integration/RouteConventionsTest` fails for a GET route it does not request (exemptions, with the reason, in `SMOKE_EXEMPT`). `SmokeTestCase::withSetting()` runs a block with a Settings override and restores the installation's own value (used for archives and rate limits); after every smoke class `tearDownAfterClass()` asserts the system data is intact (system roles, the `ALL` list, every subscriber's `subscriber` role, the dev administrator, the Administrator role's permissions). The app writes timestamps in PHP's timezone (Africa/Johannesburg) while PostgreSQL runs in UTC, so compute timestamps in PHP when inserting rows the app compares against `date()`.

Phinx configs live in `config/phinx/`. `phinx-paralegal.php` loads `.env` from `CTNLIST_INSTANCE_DIR` (required; the dev container sets `/var/www/ctnlist`); `phinx-banlist.php` loads `ban.env` from `GDB_ENV_DIRECTORY`/`GDB_ENV_FILE`. Export those before running migrations against another installation.

`database/reset-development.sql` and `database/reset-banlist-development.sql` are **destructive** and only for disposable dev databases.

The podman stack covers the main DB, mail capture and browser workflows. There is no banlist database, no real SMTP relay and (until the development route is set up) no catto-mail in dev: suppression-DB behaviour must be tested on a target installation, and catto-mail behaviour is covered by the integration tests against `tests/Support/FakeCattoMail` (a stateful fake of catto-mail's `/v1` API at the HTTP boundary: auth, Idempotency-Key replay/conflict, batch and job limits, duplicates, unsubscribe rules, the opt-out capability, fault injection including "processed but response lost"). `IntegrationTestCase::fakeCattoMail()` installs it (call it before fetching services that use `CattoMailClient`); `tests/Integration/CattoMail/CattoMailTestCase` also delivers signed webhooks through the HTTP kernel (`handle` + `terminate`).

## Migration to Symfony (complete)

ctnlist was migrated from the Fat-Free Framework (F3) to Symfony 8.1 in phases; each phase left a working app on :8180 with lint, PHPStan and the smoke suite green. Decisions: one app (no side-by-side), Doctrine DBAL repositories replace the F3 Mappers, Twig replaces string-built HTML area by area, constructor-injection DI via Symfony autowiring, and the shared-code/per-instance deployment model is kept. Done: phase 0 (smoke suite), phase 1 (directory layout), phase 2 (Symfony kernel as the front controller, with a temporary F3 bridge), phase 3 (Symfony Security: authentication, logout, ACL voter, CSRF), phase 4 (Twig layout for every page, `SiteConfig`, home/privacy/store controllers, error pages), phase 5 (list, role and ACL administration), phase 6 (campaign core services with integration tests), phase 7 (every subscriber-facing route on Symfony: sign-in requests, profile, consent links, `/subscribe`, forward, reactions, resend, `/ut`, archives, contact form), phase 8 (administration: messages and templates, the queue, sending and proofs, subscribers including `/subscribe/{token}`, bulk operations, import/export, sync and the Ecwid endpoint), phase 9 (the reports), phase 10 (F3, the bridge and `src/Legacy` removed; PHPStan level 6). In 6.0.1 the defunct Ecwid store (`/store`, `POST /ecwid-subscribe`, `APP_STORE_URL`) was removed; `TemplateRenderer` strips any leftover `{STORE}` token. Behaviour that deliberately differs from v5 is listed in `RESTORED-FUNCTIONALITY.md` ("Deliberate changes from v5"); keep that list current.

## Deployment layout

The repository is the shared code tree, installed at `/usr/local/lib/php/ctnlist/6.0.4/` (hard-coded as `$sharedDirectory` in `public_html/index.php`). Each installation has its own directory containing:
- `public_html/`: a copy of the repo's `public_html/` (`index.php`, `vendor/ckeditor5/`), used as the web root; `bin/console asset-map:compile` writes the installation's compiled assets to `public_html/assets/` (production; `App\Kernel` redirects AssetMapper's output from the shared tree to the installation);
- `.env` one directory **above** `public_html` (start from `.env.example`; `APP_ENV` is `prod`, `dev` or `test`). The Symfony runtime loads it (runtime option `project_dir` = the installation directory);
- a writable `var/` (Symfony cache and logs) and `logs/` (contact log, import log and export files).

`App\Kernel` takes the installation directory as a third constructor argument: `getProjectDir()` is the shared tree, `getCacheDir()`/`getLogDir()` are under the installation's `var/`, and `%kernel.instance_dir%` is available to services. `bin/console` needs `CTNLIST_INSTANCE_DIR`.

The suppression DB config (`ban.env`) lives outside the source tree; `config/phinx/` is its default directory.

## Architecture

**Request flow.** `public_html/index.php` → Symfony runtime → `App\Kernel` → attribute-routed controllers in `src/Controller/` (plus `app_logout` and `auth_verify` in `config/routes.yaml`, handled by the firewall). Symfony owns the session (`App\Session\DatabaseSessionHandler`, DBAL, `sessions` table; used for CSRF tokens and flash messages), error handling and the response. Unknown paths get the 404 page. Every request is recorded in the Site Log after the response is sent (`App\Log\SiteLogListener`).

**Pages.** Controllers live in `src/Controller/` (attribute routes). Every page extends `templates/base.html.twig` (blocks `title`, `description`, `content`, `stylesheets`, `javascripts`), which includes `templates/layout/`: `_navbar` (sticky site navigation and the account menu), `_admin_menu` (administration bar), `_flash` (`addFlash('info'|'danger', …)` as dismissible alerts that close after 5 s) and `_footer`. Two globals come from `App\Twig\AppExtension`: `site` (`App\Config\SiteConfig`, the non-secret installation settings built from env with the v5 defaults and fallbacks; use it instead of hard-coded site details) and `counters` (`AdminCounters`, lazily queried admin menu counts). Link with `path('route')`, not hard-coded URLs.
- The administration bar is data-driven: each item names the permission its controller's `#[IsGranted]` requires and is shown only when `is_granted()` allows it, so custom roles see their tools and administrators (all permissions via `AclVoter`) see everything. When you add an admin page, add it there with the same permission; the controller remains the security boundary.
- Styling: Bootstrap 5.3 classes first; `assets/styles/app.css` is a small application layer (system font stack, header, tables, `app-narrow` for single-purpose forms). Icons are Bootstrap Icons (`bi bi-*`) only. No inline `style=` or inline event handlers.
- Screen conventions (administration pages follow them; see `templates/admin/messages.html.twig`):
  - header: `{% embed 'layout/_page_header.html.twig' with {title, description} %}` with a `actions` block (primary action first, `btn-primary`; secondary `btn-outline-secondary`);
  - filters: a `form.card.card-body.bg-body-tertiary` (`role="search"`) with Search and Clear;
  - tables: `.table-responsive > table.table.table-hover.align-middle`, `thead.table-light`, `scope="col"`, numbers `text-end`, row actions in a right-aligned `btn-group-sm`;
  - empty results: `{% include 'layout/_empty_state.html.twig' with {message, icon, hint} %}` instead of an empty table;
  - status badges: macros in `templates/admin/_macros.html.twig` (membership, system/custom, active/inactive); data reaches Twig structured (e.g. `SubscriberRepository::reportPage()` returns each row's `memberships` as `{name, state}` pairs) — never parse display strings in templates;
  - forms: grouped in cards with the submit row in the footer (or a bordered row at the end), help text in `form-text` linked by `aria-describedby`, required fields marked `*`;
  - hierarchy: starting delivery is `btn-success`, stopping `btn-warning`, removing or suppressing `btn-danger`/`btn-outline-danger`; forms that delete, clear or suppress carry `data-confirm="Question?"` (handled in `assets/app.js`) and stay POST + CSRF;
  - actions and links to protected pages are shown only with `is_granted()` of the permission the target controller requires (navigation aid only);
  - POST outcomes render `page/result.html.twig` (`title`, `message`, optional `links` of `{label, route, permission}`);
  - pagination: `_pagination.html.twig` (Bootstrap pagination, `aria-current`, labelled first/previous/next/last, filters kept in `query`).
- Assets: `assets/` is mapped by AssetMapper (`config/packages/asset_mapper.yaml`, `importmap.php`; `{{ importmap('app') }}` loads `assets/app.js`, which imports `styles/app.css`); reference other files with `asset()`. In debug mode PHP serves `/assets/*`; production needs `asset-map:compile` per installation.
- CKEditor: pages with the HTML editor extend `templates/admin/_editor_page.html.twig`, which loads the prebuilt bundle from `public_html/vendor/ckeditor5/` and the configuration `assets/ckeditor/editor.js` (it attaches to `#mt_html`). No other page loads CKEditor.

Controller conventions (see `src/Controller/Admin/`): `#[IsGranted('perm.key')]` with ACL permission keys; forms with input use Symfony Forms (below); simple action forms (a button with hidden ids: confirm, unsubscribe, like, resend, delete, assign/unassign a role, queue/send/stop) stay plain POST with `#[IsCsrfTokenValid(Csrf::TOKEN_ID, tokenKey: Csrf::FIELD)]`; both redirect with a flash message on success (post/redirect/get); domain services (`ListManager`, `RoleManager`, …) throw `App\Validator\InvalidField` (a field name and a message) or `\InvalidArgumentException` with a message for the user, and `*NotFound` exceptions that controllers turn into 404s. Anonymous visitors on protected pages get the 403 page (`AccessDeniedEntryPoint`), as in v5. Client errors render the site's error templates even with `APP_DEBUG=true` (`App\Twig\ErrorPageDebug`); only 5xx show Symfony's exception page in debug mode. Value objects and exceptions under `src/` must be excluded from service registration in `config/services.yaml` (e.g. `SubscriberUser`), or controller arguments typed with them break autowiring.

**Forms and validation.** Input forms are Symfony Forms with the Validator component; there is no Doctrine ORM. The layers are: form type (`src/Form/Type/`, or `src/Form/Settings/` for the Settings tabs) → form model (a plain data object in `src/Form/Model/`, e.g. `ListDetails`, `MessageDraft`, `SubscribeRequest`; excluded from service registration, never an entity) → domain service/manager → DBAL repository. Form types hold no SQL and models no persistence; a model converts to the service's input (`input()`, `fields()`) and from repository rows (`fromList()`, `fromMessage()`, …).
- Validation: input rules are constraints on the model (or `constraints` on a field). Shared rules live in `src/Validator/` as compound constraints: `EmailAddress`, `WebAddress`, `Port`, `HostName`, `WholeNumber(min, max)` (number fields set `invalid_message: WholeNumber::NOT_A_NUMBER`), `ListShortcode`, `RoleKey`, and `EmailAddressList(max)` for pasted address lists (EmailNormaliser rules); reuse them rather than writing regexes. Business rules stay in services: uniqueness (pre-checked by the service for a friendly message, kept as database constraints, and a lost race is turned into the same `InvalidField`), system lists/roles, the no-escalation rule, drafts that may be incomplete.
- Controller pattern: `createForm()`, `handleRequest()`, then `isSubmitted() && isValid()` → call the service; catch `\InvalidArgumentException` and `App\Form\FormErrors::attach($form, $e)` (an `InvalidField` lands on its field, anything else on the form); re-render the same page with the form and status 422, so every value entered is kept (password fields are always rendered empty). System faults are not caught. Create and edit share one type (an option such as `create` adds the immutable key/shortcode field and its validation group). GET search forms (`SubscriberSearchType`) use `method: GET`, no CSRF and an empty block prefix (`?q=`).
- CSRF: Symfony forms use the same token as the manual forms (`framework.form.csrf_protection`: token id `ctnlist`, field `csrf`, i.e. `name[csrf]`); a bad token is a form error (422) and nothing changes.
- Rendering: the form theme (`config/packages/twig.yaml`) is `templates/form/theme.html.twig` on top of `bootstrap_5_layout.html.twig`: every widget gets `aria-describedby` (help and errors) and `aria-invalid`, forms get `novalidate` (server-side validation only, shown the same way everywhere), and labels of required fields show a red asterisk (`app.css`). Lay fields out with `form_row()` in the screen's grid (see `templates/admin/message_form.html.twig`); render choices by hand only to add descriptions (subscribe page, role permissions), keeping `form_errors()`.
- Typed POST forms (anything with fields to validate) are Symfony Forms even when small (e.g. `QueueRotationType`, `ExportType`); a value outside the offered choices is a form error, never passed on.
- Tests: integration tests can build a form from `FormFactoryInterface` (see `tests/Integration/Form/SettingsFormTest.php`); smoke tests submit the rendered form with `submitForm()`/`submitAndFollow()` and assert the field error id (`<form>_<field>_error1`), the kept values and that nothing was stored.

**HTTP and security conventions.** Enforced over the whole route table by `tests/Integration/RouteConventionsTest`.
- Methods: GET never changes state; actions are POST (e.g. `/export` writes files, `/sync` writes remote databases, `/logout` ends the session: all POST with CSRF). Deliberate GET side effects are tracking only: the `/ut/{token}/{muid}` open pixel, the archive view counter and the engagement bump when a subscriber opens their contact-form link. `GET /auth/verify` consumes a one-time sign-in token (link scanners that prefetch could use it up; a confirm-click page is a possible later change).
- CSRF: every POST route is a Symfony form (its own token) or has `#[IsCsrfTokenValid]`; the only exemptions are `cattomail_webhook` (HMAC signature), `consent_unsubscribe_link` (RFC 8058 one-click, HMAC-signed link) and `app_logout` (firewall `enable_csrf`, field `csrf`). One token id (`ctnlist`) and field (`csrf`) everywhere.
- Authorisation: every `App\Controller\Admin\` route declares `#[IsGranted('perm.key')]`, except `admin_subscriber`/`admin_subscriber_save` (`/subscribers/{token}[/{muid}]`: the subscriber themself or `subscribers.manage`, checked in the controller). Twig `is_granted()` only hides links. `RoleManager` enforces no escalation (a role or permission can be granted only by someone holding all of it; changing a role's permissions needs `acl.manage` in the service too).
- Redirects go to generated routes or to whitelisted internal paths only (`LoginReturnPath` actions, `RoleController::back()` limited to `/roles…`).
- Output: Twig autoescaping everywhere; the single `sanitize_html` use is message HTML on the public archive page (`config/packages/html_sanitizer.yaml`, sanitizer `app.message_html`: no script, event handlers, `javascript:` links, frames or forms; layout attributes kept). Message HTML is written by holders of `messages.manage`, which custom roles can have, so it is never printed `|raw` on the site. Mail is not sanitised. `TemplateRenderer` escapes subscriber names and configured URLs in the HTML part.
- Headers: `App\Http\SecurityHeadersListener` sets `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin` (subscriber UUIDs are in paths), `Permissions-Policy`, HSTS on HTTPS requests and a CSP of `frame-ancestors 'self'; base-uri 'self'; object-src 'none'; form-action 'self'`. A script/style CSP needs nonces for the import map and the CDN/CKEditor sources; it is a later change. Static files served by nginx do not get these headers.
- Cookies: the auth cookie is HttpOnly, SameSite=Lax, host-only, path `/`, and Secure whenever the request is HTTPS or `APP_BASE_URL` is https (so a proxy that hides HTTPS cannot downgrade it); the PHP session cookie (CSRF and flashes) is `cookie_secure: auto`, HttpOnly, Lax.
- Rate limits: sign-in links use their own database counters (`AUTH_MAGIC_LINK_*`); `App\Http\RequestThrottle` (symfony/rate-limiter, sliding hour, cache pool `cache.rate_limiter`) limits contact messages per IP and per address (`CONTACT_RATE_LIMIT`, default 5) and forwards/resends per subscriber (`FORWARD_RATE_LIMIT`, default 10; holders of `messages.manage` are not limited); over the limit the page answers 429. Both are Settings. No CAPTCHA.
- SQL: DBAL parameters only; `LIMIT`/`OFFSET` are clamped integers; user search terms go through `App\Repository\Like` (`%`, `_` and `\` literal).
- Logging privacy: never log secrets, setting values (only names), tokens or message bodies. The Site Log stores the path without the query string (the sign-in token travels there) and masks the one-click unsubscribe signature (`SiteLog::loggablePath()`). Web-server access logs are the installation's responsibility: drop query strings for `/auth/verify`.
- Development aids are refused or ignored outside `APP_ENV` dev/test: `SUPPRESSION_PROVIDER=none` and `CATTOMAIL_API_CONNECT_HOST` (`tests/Unit/Config/DevelopmentOnlyTest`).
- Frontend sources: Bootstrap 5.3.8 and Bootstrap Icons 1.13.1 come from jsDelivr with SRI and `crossorigin`. They are kept on the CDN deliberately: AssetMapper's `importmap:require` would vendor the CSS but not the icon fonts it references, so localising them is not a one-step change. CKEditor 5 (48.3.0, GPL licence key) is a prebuilt bundle in `public_html/vendor/ckeditor5/`, loaded only on the editor pages.

**Settings overrides.** `App\Config\RuntimeSettings` resolves the env vars listed in `App\Config\SettingsCatalogue` (site identity, contact details, mail sender, the transactional SMTP server, contact form, subscription messages, archives, sign-in limits) as database override → `.env` → built-in default (the catalogue's `default`). Overrides live in `options` under `setting:<ENV_NAME>` (`SettingRepository`; `o_secret`, `o_updated_at`, `o_updated_by_s_id`); the database holds overrides only, `.env` is never written, and saving the inherited value (or "Reset override"/"Reset section") deletes the override. `/settings` (`Admin\SettingsController`, permission `settings.manage`, administrators have it) shows one tab per group, each its own Symfony form (`App\Form\Settings\SettingsGroupType` built from the catalogue, rules from `SettingConstraints`; the transactional SMTP server is the nested `SmtpServerType`; `SettingsFormData` converts between settings and form data, never loading a secret; invalid input is shown at its field and nothing in the tab is saved) (the URL hash, e.g. `#smtp`, selects the tab; `data-remember-tab` in `assets/app.js`), with each field's source (Database/.env/Default); field layout comes from the catalogue's `width`, `heading` and short `tab` names. Read these settings through `SiteConfig` (built from `RuntimeSettings::environment()`, which excludes secrets) or `RuntimeSettings::get()/int()`, never `%env()%`/`#[Autowire(env:)]`: `SmtpServerPool` is built lazily by `SmtpServerPoolFactory` (it receives the decrypted `MAILER_DSN`), `MagicLinkRequester` and `AuthCookie` read their limits from `RuntimeSettings`. The secret setting `MAILER_DSN` is encrypted with `SettingsCipher` (AES-256-GCM, dedicated `APP_SETTINGS_KEY` = 32 random bytes Base64, format `enc:v1:<key id>:<base64(nonce|tag|ciphertext)>`), never rendered (password fields stay empty; empty keeps the current value) and never logged; a secret that cannot be decrypted raises `SettingsCipherException` when mail needs it (the Settings page shows the problem) instead of falling back. Changes apply from the next request or email. Keep infrastructure (secret keys, `CATTOMAIL_*`, `DB_*`, `GDB_*`, suppression provider, URLs, paths, cookie names, `APP_ADMIN_EMAIL`, `APP_TIMEZONE`, `TRUSTED_PROXIES`) out of the catalogue. To add a setting: add it to the catalogue with type, validation bounds and default, and read it as above.

**Two PostgreSQL databases.** Main DB (`DB_*`) and a separate, shared global suppression DB (`GDB_*`). Each has its own migration directory and Phinx config. `SUPPRESSION_PROVIDER` (`banlist` default, `none` for dev/test) selects the source. Symfony code uses `App\Suppression\SuppressionChecker` (`BanlistSuppressionChecker` reads `ban.env` itself and connects lazily; `NullSuppressionChecker`); it is ctnlist's own suppression source and is not catto-mail's (which catto-mail enforces itself). `isSuppressed()` applies the v5 address cleanup rules first (`App\Subscriber\EmailNormaliser`, moved verbatim from `SubscribersM`; they deliberately make .org, .gov(.za), .ac.za and similar addresses invalid, and an unusable address counts as suppressed).

**Identity and consent.** `subscribers` is the canonical identity table, keyed publicly by a permanent UUIDv7 (`s_uuid`, generated by the SQL function `ctn_uuid_v7()`); URLs use it as `{token}`. Auth is passwordless magic-link, on Symfony Security (`config/packages/security.yaml`, `src/Security/`):
- Requesting a link (`POST /login`, `POST /auth/request`; `AuthController`, `MagicLinkRequester`): creates the identity for a new address (no consent; a new subscriber asking for the profile is sent on to confirm ALL), rate-limits per address and IP (`AUTH_MAGIC_LINK_*`), stores a SHA-256 hash in `auth_login_tokens` with a whitelisted return action, and mails the link via `TransactionalMailer`.
- Subscriber links (profile, consent, forward, reactions, resend) act only for the signed-in subscriber they belong to; anyone else gets `templates/auth/prompt.html.twig` (`AuthenticationPrompt`: masked address, sends a link that returns to the action). Pages for signed-in subscribers redirect anonymous visitors to `/login`, as in v5; admin pages give them the 403 page.
- The `main` firewall is **stateless**: auth state is the auth cookie (`AUTH_SESSION_COOKIE`, a random token whose hash identifies an `auth_sessions` row), not the PHP session. `MagicLinkAuthenticator` handles `GET /auth/verify` (claims the token atomically, records the login, bootstraps the `APP_ADMIN_EMAIL` administrator, creates the auth session, sets the cookie, redirects via `LoginReturnPath`). `AuthSessionAuthenticator` authenticates every other request carrying the cookie; a bad cookie leaves the request anonymous and `AuthCookieClearingListener` clears it. `/logout` is the firewall logout (`LogoutListener` revokes the auth session).
- `SubscriberUser` (identifier: `s_uuid`) carries role keys (roles `ROLE_<KEY>`, e.g. `ROLE_ADMINISTRATOR`) and ACL permission keys. Authorise with `is_granted('lists.manage')` / `#[IsGranted]`; `AclVoter` grants administrators everything, as v5 did.
- Role administration (`Admin\RoleController`, `App\Security\RoleManager`, `RoleRepository`): `/roles` lists roles with member counts, finds subscribers (email, name or UUID; at most 20 results, no full subscriber list in the page) and assigns roles; `/roles/{id}[/{page}]` shows one role with its permissions and paged members, renames/describes it, removes it from members and deletes it. `roles.manage` covers all of that; changing a custom role's permissions (`POST /roles/permissions`) needs `roles.manage` and `acl.manage` (so `acl.manage` is only meaningful with `roles.manage`). Role keys are fixed after creation (name/description editable). System roles (`administrator`, `subscriber`) cannot be renamed, deleted, re-permissioned or removed from subscribers here; every subscriber holds `subscriber` (insert trigger). Non-administrators cannot assign a role, or grant a permission, that they do not hold themselves (no escalation, e.g. to Administrator). Deleting a custom role removes its `subscriber_roles` rows first (`ON DELETE RESTRICT`); `role_permissions` cascades.
- Repositories (`src/Repository/`) are DBAL, return arrays, and take timestamps from the injected clock in PHP's timezone (`Kernel::boot()` sets it from `APP_TIMEZONE`). DBAL's `fetchOne()` returns `false` both for "no row" and for a boolean `FALSE` column, so read boolean columns with `fetchAssociative()`. A subscriber is eligible for a list only when `list_subscribers.ls_confirmed = TRUE AND ls_unsubscribed = FALSE`. The `ALL` system list is immutable, optional, and must **never** be attached to a message automatically. Its shortcode is `ALL`; list shortcodes are 3–6 uppercase letters/digits.

**Mail delivery.** Campaign content (queue sends, proofs, resends, forwards) is rendered by ctnlist per recipient and delivered by catto-mail (below); transactional mail goes through ctnlist's SMTP. The queue is built and sent from the administrator pages in `App\Controller\Admin\QueueController` (`/queuelist`, `/advanced-queue`, `/processqueue`, `/stop-send`, proofs via `/sendtome`):
- `App\Mail`: `SmtpServerPool` (the transactional server: `MAILER_DSN`), `MailConnection` (one opened transport per use, created via `mailer.transport_factory` so test mail is captured; throttled to `MAIL_RATE_PER_MINUTE`), `TransactionalMailer` (notifications with admin BCC, sign-in links, list invitations, contact acknowledgements). There is no campaign SMTP path.
- `App\Log`: `SendLog` (every handoff), `MessageLog` (smlog once-only guard, activity counters via `MessageActivity`, the message-views report), `SiteLog` + `SiteLogListener` (one `sitelog` row per request, written on `kernel.terminate`). Report queries: `SendLogRepository`, `SiteLogRepository`; pages in `Admin\ReportController` (`logs.view`).
- `App\Campaign`: `TemplateRenderer` (v5 MergeTemplate ported replacement-for-replacement and verified identical; replacement order matters), `ArchiveService`, `MessageService` (drafts saved exactly as supplied, first-queue preparation, `sendProof()` to any valid address — no subscriber lookup or record, rendered for `TemplateRenderer::PROOF_RECIPIENT` without the tracking pixel, Send Log only — and `sendTo()` resends/forwards to subscribers).
- `App\Subscriber\SubscriberAdmin`: the administrator subscriber form (priority + 100 on save, `UPDATE-PROFILE` notification), bulk subscribe/unsubscribe (list, or global domain/bounce/spam suppression), import, the two export files and `SYNC_DATABASES_JSON` synchronisation. Import logs and export files go to `APP_LOG_DIR` (default: the installation's `logs/`). Adding subscribers never grants consent.
- `App\Queue`: `QueueBuilder` (union of selected lists, once-only, suppression → unsubscribe from all lists, rotation; subscribers whose `s_delivery_state` is not `ok` are not selected), `QueueProcessor` (v5 ProcessQueue contract — queue order, stop flag, `m_max_send`, eligibility and suppression re-checked per message — renders each recipient and stages them with `CattoMailSender`, removing the queue row in the same transaction; returns a `SendOutcome`: submitted, deferred (kept for the worker) or failed).
- `App\Subscriber`: `Engagement` (v5 priority bump/set/reset), `ConsentService` (confirm/unsubscribe with the v5 effects), `SubscriptionService` (v5 SimpleSubscribe: pending membership plus invitations), `ProfileService`, `ContactService`; `App\Campaign\ForwardService`, `ReactionService`.
- Profile pictures: `/edit-profile` has a picture card (`ProfileImageType` → `ProfileImageUpload`; `assets/profile_image.js` lets the subscriber position, zoom and rotate the picture and posts the cropped square as a PNG data URL in `edited`; without JavaScript the file is posted). `App\Subscriber\ProfileImage` (value object, needs ext-gd; ext-exif for phone-photo orientation) validates bytes, not names or Content-Type (PNG/JPEG/WebP, ≤ 8 MB, ≤ 64 megapixels checked from the header before decoding), applies EXIF orientation, takes the centred square and always re-encodes a 256 px PNG. `ProfileImages` saves/removes and gives the URL pages show: `GET /profile/image?v=<version>` (the signed-in subscriber's own picture only, cacheable because a new picture is a new version) or the placeholder asset `images/avatar-placeholder.svg`. Stored in `subscriber_images` (`SubscriberImageRepository`, bytes as base64 in SQL). Twig `profile_image_url(app.user)` (null: placeholder) feeds the navbar thumbnail and the profile pages.
- Lists use `App\Http\Pagination` (v5 `?r=` rows per page) and `templates/_pagination.html.twig`.

**catto-mail integration** (`src/CattoMail/`, README "catto-mail integration"). ctnlist uses only catto-mail's public HTTPS `/v1` API and its signed webhooks, never its database; the contract is catto-mail's `docs/api/openapi.v1.yaml` (read it there; do not copy it here, and report rather than implement any contract change).
- `CattoMailConfig` (from `.env` via `CattoMailConfigFactory`; `CATTOMAIL_*`; never Settings, never rendered or logged, `__debugInfo` redacts, not serialisable). `CattoMailClient` is the only HTTP caller: Bearer key, caller-supplied Idempotency-Key, in-place retries of timeouts/5xx/429/`idempotency-in-progress` with the same key (`CattoMailUnavailable`), refusals as `CattoMailRejected` with problem details; messages are redacted.
- Outbox (`CattoMailSendRepository`, tables `cattomail_runs` → `cattomail_send_jobs` (≤ 10,000 recipients, one message/list/sender each, `external_reference` `<run uuid>/<n>`, exact create body stored) → `cattomail_batches` (≤ 500, key per batch) → `cattomail_recipients` (`crp_uuid` = `external_recipient_reference`; rendered content kept until the batch is accepted)). `CattoMailSender` stages, uploads full batches, splits and seals jobs, and on seal hands recipients off (Send Log + smlog). Counts are derived from recipient rows at batch/job close (no per-recipient counter updates). `OutgoingMessageFactory`: subscription jobs with `List-Id` `<list name> <shortcode.APP_DOMAIN>` and a per-recipient `UnsubscribeLinks` one-click URL (signed, https, no tracking; `consent_unsubscribe_link`), transactional jobs for proofs. Every key is generated and stored before its request; retries never generate a new one.
- Webhooks: `CattoMailWebhookController` (`POST /cattomail/webhook`, no session/CSRF) → `WebhookSignature` (catto-mail's exact headers `Smarthost-Signature`/`Smarthost-Event-Id`; HMAC over `<t>.<raw body>`, current + previous secret, 5-minute tolerance, before parsing) → `CattoMailWebhookRepository::store()` (unique event id; duplicates acknowledged) → 200; `CattoMailWebhookTerminateListener` runs `WebhookProcessor` after the response. `SendJobSync` and `AddressValidation::apply()` map job and message/result states (never backwards; unknown statuses ignored); `DeliveryProblems` applies hard bounces (`s_delivery_state` hard_bounced, `s_bounces`, `m_bounces`, queue rows removed) and complaints (complained, unsubscribe from all lists) once per delivery (`crp_effect`).
- `CattoMailWorker` / `bin/console ctnlist:cattomail:work` (cron): unprocessed webhook events, unsealed jobs (finished or abandoned runs), opt-outs, validation submissions, and polling of jobs without a final state older than `CATTOMAIL_RECONCILE_AFTER_SECONDS`.
- `GlobalOptOut`: only an explicit subscriber request (`POST /no-contact`, offered when `CATTOMAIL_GLOBAL_OPTOUT_ENABLED`) creates a catto-mail global opt-out (and unsubscribes from all ctnlist lists); `POST /no-contact/withdraw` lifts it. Ordinary unsubscribes (`ConsentService`, including the one-click link and the ctnlist banlist scopes) are never sent to catto-mail.
- Admin: `Admin\DeliveryController` (`logs.view`; requeue of a refused job needs `queue.process`, `SendJobAdmin`):
  - `/delivery` is the integration status page: configuration without secrets, `POST /delivery/check` (`CattoMailHealth` → `CattoMailClient::probe()`: `GET /v1/send-jobs/<PROBE_ID>`, 404 = authenticated; states not_configured, dns, connection, tls, auth_rejected, forbidden, unavailable, unexpected, ok; last result in `options`);
  - `CattoMailActivity` (last API success/error, worker heartbeat, in `options`) and `CattoMailStatusRepository` counts;
  - `/delivery/run/{uuid}`: one ctnlist run and its catto-mail jobs;
  - `/delivery/webhooks/{page}?f=`: webhook events with their related job; raw bodies are never shown;
  - message, job and recipient pages.

  `Admin\AddressValidationController` (`/address-validation…`, `subscribers.manage`; lists over 10,000 become "part n of N" jobs, and the administrator is told the total). The subscriber page shows the delivery block (hard bounce or complaint, since when) with "Clear the sending block" (POST + CSRF, `subscribers.manage`, logged by UUID; clears the block only, never memberships or consent) and the latest validation. Validation results never change subscribers (suggestions are never applied; `unknown` and `temporarily_unverifiable` are kept as such).
- Robustness:
  - **Errors:** `CattoMailClient` puts advice before refusals (401 key, 403 not permitted, sender-domain field errors) and includes catto-mail's field errors; transport failures are classified (dns/tls/connection) and redacted of the key and webhook secrets.
  - **Queue staging:** a queue row is removed only inside its staging transaction, and only if this run removed it (`QueueRowClaimed` rolls back otherwise); `uq_crp_campaign_delivery` allows one active campaign delivery per (message, subscriber).
  - **States:** `updateJobState` is one monotonic SQL statement; bounce/complaint claims and effects commit together.
  - **Opt-outs:** `uq_cgo_open_per_subscriber` with `ON CONFLICT DO NOTHING` makes a double submit safe.
  - **Worker:** `WorkerLock` (advisory lock) runs one worker at a time; `ctnlist:cattomail:work` prints counts and exits 1 only on failures.
  - **Fake:** `tests/Support/FakeCattoMail` uses catto-mail's real problem types (`forbidden`, `validation-error` with field errors, `recipient-limit-exceeded`, `batch-too-large`, `job-not-collecting`, `job-not-submittable`, `empty-job`); `finishOnRead` simulates an instant catto-mail.
- Global opt-out needs the "I understand" box (server-checked, `confirm=yes`). The subscriber is told the real outcome (active, pending report, refused). Withdrawal is `POST /v1/global-suppressions/{id}/lift`, naturally idempotent and retried by the worker. Neither re-subscribes anyone.

## Invariants to preserve

- Every successful email handoff is logged to `sendlog`; for campaign content the handoff is catto-mail sealing its send job.
- Every campaign-content delivery goes through `CattoMailSender` (no other campaign path) and logs to `sendlog`; deliveries to subscribers (queue, resend, forward) also log to `smlog`. Proofs go to an arbitrary address with no subscriber: they are logged in `sendlog` as PROOF only and never touch `smlog`, the queue, consent or memberships. The unique `(subscriber UUID, message MUID)` row in `smlog` is the once-only delivery guard for normal queue sends.
- Global email/domain suppression (ctnlist's banlist) is checked at confirmation, queue build and immediately before staging. A global unsubscribe disables all local list memberships. catto-mail's own suppressions are never queried (it enforces them).
- Every catto-mail Idempotency-Key is persisted before its request and reused by every retry; webhooks are verified before parsing and de-duplicated by event id; ordinary unsubscribes never become catto-mail global opt-outs.
- Messages and templates may be saved as incomplete drafts with no lists; store exactly what the administrator selected.
- State-changing POST routes validate CSRF and forms include the token: Symfony forms do it themselves (same token id `ctnlist`); simple action forms use `#[IsCsrfTokenValid(Csrf::TOKEN_ID, tokenKey: Csrf::FIELD)]` in controllers and `<input type="hidden" name="csrf" value="{{ csrf_token('ctnlist') }}">` in templates (Symfony's session-stored token manager). GET requests never change state (tracking excepted); see "HTTP and security conventions".
- **No backward compatibility.** ctnlist is not in production and has no data to preserve. Do not add aliases, legacy link/route forms or upgrade migrations: change the source of truth directly (schema changes go into `20260716120000_create_phase3a_schema.php`, then `bin/dev reset-db`). This applies until the user announces go-live.
