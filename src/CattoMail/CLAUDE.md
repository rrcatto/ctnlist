# catto-mail integration

ctnlist uses only catto-mail's public HTTPS `/v1` API and its signed webhooks, never its database. The contract is `docs/api/openapi.v1.yaml` in the catto-mail repository: read it there, do not copy it here, and report a needed contract change rather than implementing it. README "catto-mail integration" describes the feature for operators.

**Configuration and client.**
- `CattoMailConfig` is built from `.env` (`CATTOMAIL_*`) by `CattoMailConfigFactory`. It is never a Setting and never rendered or logged; `__debugInfo` redacts it and it cannot be serialised.
- `CattoMailClient` is the only HTTP caller: Bearer key and a caller-supplied Idempotency-Key. Timeouts, 5xx, 429 and `idempotency-in-progress` are retried in place with the same key (`CattoMailUnavailable`); refusals are `CattoMailRejected` with the problem details. Error messages put advice before the refusal (401 key, 403 not permitted, sender-domain field errors), include catto-mail's field errors, classify transport failures (dns, tls, connection) and are redacted of the key and webhook secrets.
- Every key is generated and stored before its request; a retry never generates a new one.

**Sending.**
- Outbox tables (`App\Repository\CattoMailSendRepository`): `cattomail_runs` → `cattomail_send_jobs` (≤ 10,000 recipients, one message, list and sender each; `external_reference` `<run uuid>/<n>`; the exact create body is stored) → `cattomail_batches` (≤ 500, one key per batch) → `cattomail_recipients` (`crp_uuid` is the `external_recipient_reference`; rendered content is kept until its batch is accepted).
- `CattoMailSender` stages recipients, uploads full batches, and splits and seals jobs. Sealing is the handoff: Send Log, plus smlog for subscribers. Counts are derived from recipient rows when a batch or job closes, never kept as per-recipient counter updates.
- A queue row is removed only inside its staging transaction, and only if this run removed it (`QueueRowClaimed` rolls back otherwise); `uq_crp_campaign_delivery` allows one active campaign delivery per (message, subscriber).
- `OutgoingMessageFactory`: subscription jobs carry `List-Id` `<list name> <shortcode.APP_DOMAIN>` and a per-recipient signed https one-click unsubscribe URL (`UnsubscribeLinks`, route `consent_unsubscribe_link`, no tracking); proofs are transactional jobs.

**Webhooks and states.**
- `POST /cattomail/webhook` (`CattoMailWebhookController`, no session or CSRF; bodies over 1 MiB, declared or actual, are refused first) → `WebhookSignature` (headers `Smarthost-Signature` and `Smarthost-Event-Id`; HMAC over `<t>.<raw body>`; current and previous secret; 5-minute tolerance; checked before parsing) → `CattoMailWebhookRepository::store()` (unique event id; duplicates acknowledged) → 200. `CattoMailWebhookTerminateListener` runs `WebhookProcessor` after the response.
- `SendJobSync` and `AddressValidation::apply()` map job and message/result states: never backwards (`updateJobState` is one monotonic statement), and unknown statuses are ignored.
- `DeliveryProblems` applies hard bounces (`s_delivery_state` hard_bounced, `s_bounces`, `m_bounces`, queue rows removed) and complaints (complained, unsubscribed from all lists) once per delivery (`crp_effect`); the claim and its effects commit together.
- Address validation results never change subscribers: suggestions are never applied, and `unknown` and `temporarily_unverifiable` are kept as such. Lists over 10,000 addresses become "part n of N" jobs, and the administrator is told the total.

**Global opt-out** (`GlobalOptOut`). Only an explicit subscriber request (`POST /no-contact`, offered when `CATTOMAIL_GLOBAL_OPTOUT_ENABLED`, with the server-checked "I understand" box, `confirm=yes`) creates a catto-mail global opt-out; it also unsubscribes the subscriber from all ctnlist lists. `POST /no-contact/withdraw` lifts it (`POST /v1/global-suppressions/{id}/lift`, idempotent, retried by the worker). Neither re-subscribes anyone, and the subscriber is told the real outcome (active, pending report, refused). Ordinary unsubscribes, including the one-click link and the banlist scopes, are never sent to catto-mail. `uq_cgo_open_per_subscriber` with `ON CONFLICT DO NOTHING` makes a double submit safe.

**Worker.** `CattoMailWorker` (`ctnlist:cattomail:work`, cron every minute; one at a time through `App\Maintenance\DatabaseLock`; exits 1 only on failures) processes unprocessed webhook events, unsealed jobs of finished or abandoned runs, opt-outs and validation submissions, and polls jobs without a final state older than `CATTOMAIL_RECONCILE_AFTER_SECONDS`. `CattoMailActivity` keeps the last API success and error and the worker heartbeat in `options`; `App\Maintenance\StuckWork` defines stuck work (2 × the reconcile interval, at least 10 minutes) and the job categories.

**Administration.** `Admin\DeliveryController` (`logs.view`) and `Admin\AddressValidationController` (`subscribers.manage`). `/delivery` shows the configuration without secrets and a connection check (`CattoMailHealth` → `CattoMailClient::probe()`: `GET /v1/send-jobs/<PROBE_ID>`, where 404 means authenticated). Raw webhook bodies are never shown. Recovery actions are POST + CSRF and logged with the administrator's UUID; they only ask catto-mail again or repeat stored requests, and nothing sets a state by hand: retry an unsealed job (`queue.process`; refused while its run is staging or catto-mail is unconfigured), reprocess an unprocessed or failed event (`queue.process`), retry a validation submission or an opt-out (`subscribers.manage`). "Clear the sending block" on a subscriber page (`subscribers.manage`) clears the block only, never memberships or consent.

**Tests.** Integration tests use `tests/Support/FakeCattoMail`, a stateful fake of the `/v1` API at the HTTP boundary: auth, Idempotency-Key replay and conflict, batch and job limits, duplicates, unsubscribe rules, the opt-out capability, catto-mail's real problem types and fault injection (including "processed but response lost"); `finishOnRead` simulates an instant catto-mail. Call `IntegrationTestCase::fakeCattoMail()` before fetching any service that uses `CattoMailClient`. `tests/Integration/CattoMail/CattoMailTestCase` delivers signed webhooks through the HTTP kernel (`handle` + `terminate`).
