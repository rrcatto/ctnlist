# catto-mail integration

ctnlist uses only catto-mail's public HTTPS `/v1` API and its signed webhooks, never its database. The contract is `docs/api/openapi.v1.yaml` in the catto-mail repository: read it there, do not copy it here, and never work around it in ctnlist. README "catto-mail integration" describes the feature for operators.

**The catto-mail repository** (`github.com/rrcatto/catto-mail`, usually checked out beside this one as `../catto-mail`).
- Read there: `docs/api/openapi.v1.yaml` (the contract; `info.version` is its version), `docs/api/integration-guide.md` (the contract explained for clients), `docs/contracts/status-vocabulary.yaml` (every status and event value) and `docs/integration/ctnlist.md` (catto-mail's record of this integration, and of the ctnlist work it is waiting for).
- A needed contract change is reported to the owner. It is made in catto-mail, and only when the owner asks for it in that task. catto-mail has its own `CLAUDE.md`, specification and gate; its rules differ from ctnlist's (schema changes are new migrations there, for one).
- `FakeCattoMail` is a hand-written copy of the contract's behaviour and the only catto-mail the tests see. When the contract changes, change the fake to match it exactly, together with `CattoMailClient`; never loosen the fake to make a test pass.
- **Contract version.** `CattoMailConfig`, `CattoMailClient` and `FakeCattoMail` follow OpenAPI 1.0.0-draft.10, except in three places:
  - The webhook event `repermission.responded` (a recipient's answer to a re-permission message that catto-mail sent from an address batch) is stored and ignored as an unknown type. catto-mail's `docs/integration/ctnlist.md` specifies the handling. The event's `data.batch.list_id` is the part of ctnlist's List-Id inside the angle brackets: `<shortcode>.<APP_DOMAIN>` in lower case (`OutgoingMessageFactory::forList()`).
  - `429` with the problem type `quota-exceeded` (the client's daily or monthly quota; its `Retry-After` can be hours) is handled like a rate limit: retried in place, then by the worker on every pass.
  - catto-mail can set a client's recipients per send job below 10,000 and an installation's recipients per batch below 500. ctnlist holds both as constants (`CattoMailConfig::MAX_*`), so a lower limit refuses the job (`422`, `recipient-limit-exceeded` or `batch-too-large`).

  Timestamps changed from UTC (`Z`) to the installation's offset (`+02:00`); `DeliveryProblems::timestamp()` reads both.

**Connection** (README "catto-mail integration", *Connecting*; catto-mail's integration guide, section 15).
- `ConnectFlow` runs catto-mail's connect flow for an administrator on the Delivery page (`Admin\DeliveryConnectionController`): `start()` keeps a state and a PKCE code verifier (the verifier encrypted, in `options` under `cattomail:connect:pending`, for an hour) and returns the address of the service's connect page; `complete()` checks the state and the administrator, exchanges the code (`CattoMailClient::exchangeConnectCode()`, the one call without an API key) and stores what is handed over; `disconnect()` asks the service to end the connection (`deleteConnection()`, with the stored key, never the configured one) and only then clears it. Every refusal is an `\InvalidArgumentException` for the administrator.
- `ConnectionStore` keeps the connection in the Settings store under the `.env` names (`setting:CATTOMAIL_API_BASE_URL`, `…_API_KEY`, `…_WEBHOOK_SECRET`, the key and the secret encrypted by `SettingsCipher`) and its details (`setting:CATTOMAIL_CONNECTION`: service, catto-mail client, endpoint; no secret). The names are not in `SettingsCatalogue`, so the Settings page never shows them.
- **`.env` wins, value by value** (`CattoMailConfigFactory`): the address, the key and the secret each come from `.env` when it sets them, otherwise from the connection (`CattoMailConfig::source()`, `usesConnection()`, `envSettings()`). `ConnectFlow::obstacle()` refuses to start while `.env` sets one of the three, without `APP_SETTINGS_KEY`, or (outside dev/test) without https.
- Never put a key, a secret, the code or the verifier in an address, a log, a flash message or a page; `CattoMailClient` redacts the secrets of a connect call from its errors. A GET never changes state here either: the callback only shows the Finish form (`data-autosubmit`, `assets/app.js`), and `complete` is a POST with CSRF. Connect answers with a page that forwards the browser (`<meta http-equiv="refresh">`), not a redirect: the CSP's `form-action 'self'` stops a form from ending at another site.
- Only administrators connect or disconnect (the controller checks `isAdministrator()` besides `settings.manage`).
- `SendingDomainCheck` keeps catto-mail's last answer about the client's sending domains (from the exchange, from `CattoMailHealth::check()` and from the worker on every pass while the From domain cannot send, `GET /v1/sending-domains`) and says whether the domain of `MAIL_FROM_ADDRESS` can send; the Delivery page warns when it cannot, and then redraws itself every 30 seconds (htmx) from what is stored.
- `CattoMailConfig` is built once per process: a worker running with `--loop` must be restarted after connecting or disconnecting. `ConnectFlow::changedAt()` keeps the Delivery page from calling a worker's older fingerprint "another configuration".

**Configuration and client.**
- `CattoMailConfig` is built by `CattoMailConfigFactory` from `.env` (`CATTOMAIL_*`) and the stored connection (above). It is never an editable Setting and never rendered or logged; `__debugInfo` redacts it and it cannot be serialised. `CATTOMAIL_API_CONNECT_HOST` (`host[:port]`) and `CATTOMAIL_WEBHOOK_URL` are development aids, ignored outside dev/test.
- `CattoMailClient` is the only HTTP caller: Bearer key and a caller-supplied Idempotency-Key (the connect operations take their own API root and key, and stay out of the configured client's activity record). Timeouts, 5xx, 429 and `idempotency-in-progress` are retried in place with the same key (`CattoMailUnavailable`); refusals are `CattoMailRejected` with the problem details. Error messages put advice before the refusal (401 key, 403 not permitted, sender-domain field errors), include catto-mail's field errors, classify transport failures (dns, tls, connection) and are redacted of the key and webhook secrets.
- Every key is generated and stored before its request; a retry never generates a new one.

**Sending.**
- Outbox tables (`App\Repository\CattoMailSendRepository`): `cattomail_runs` → `cattomail_send_jobs` (≤ 10,000 recipients, one message, list and sender each; `external_reference` `<run uuid>/<n>`; the exact create body is stored) → `cattomail_batches` (≤ 500 recipients and ≤ 8 MiB of JSON as sent, since every recipient carries its own rendered copy and catto-mail refuses requests over 10 MiB; one key per batch) → `cattomail_recipients` (`crp_uuid` is the `external_recipient_reference`; rendered content is kept until its batch is accepted).
- `CattoMailSender` stages recipients, uploads full batches, and splits and seals jobs; a recipient joins only a job still open (`lockOpenJob`, in the staging transaction), otherwise the run continues in a new job. Sealing is the handoff: Send Log, plus smlog for subscribers (`recordSubmission`, which `SendJobSync` also runs when catto-mail reports a job sealed whose handoff was never recorded). Counts are derived from recipient rows when a batch or job closes, never kept as per-recipient counter updates.
- A queue row is removed only inside its staging transaction, and only if this run removed it (`QueueRowClaimed` rolls back otherwise); `uq_crp_campaign_delivery` allows one active campaign delivery per (message, subscriber).
- `OutgoingMessageFactory`: subscription jobs carry `List-Id` `<list name> <shortcode.APP_DOMAIN>` and a per-recipient signed https one-click unsubscribe URL (`UnsubscribeLinks`, route `consent_unsubscribe_link`, no tracking); proofs are transactional jobs. Proofs reach catto-mail only while `MAIL_PROOF_SMTP` is empty: otherwise `App\Mail\ProofMailer` hands them to Mailpit, except the proof of `ctnlist:cattomail:check --e2e`, which is this integration's own check.

**Webhooks and states.**
- `POST /cattomail/webhook` (`CattoMailWebhookController`, no session or CSRF; bodies over 1 MiB, declared or actual, are refused first) → `WebhookSignature` (headers `Smarthost-Signature` and `Smarthost-Event-Id`; HMAC over `<t>.<raw body>`; current and previous secret; 5-minute tolerance; checked before parsing) → `CattoMailWebhookRepository::store()` (unique event id; duplicates acknowledged) → 200. `CattoMailWebhookTerminateListener` runs `WebhookProcessor` after the response.
- `SendJobSync` and `AddressValidation::apply()` map job and message/result states: never backwards (`updateJobState` is one monotonic statement), and unknown statuses are ignored.
- `DeliveryProblems` applies hard bounces (`s_delivery_state` hard_bounced, `s_bounces`, `m_bounces`, queue rows removed) and complaints (complained, unsubscribed from all lists) once per delivery (`crp_effect`); the claim and its effects commit together.
- Address validation results never change subscribers: suggestions are never applied, and `unknown` and `temporarily_unverifiable` are kept as such. Lists over 10,000 addresses become "part n of N" jobs, and the administrator is told the total.

**Global opt-out** (`GlobalOptOut`). Only an explicit subscriber request (`POST /no-contact`, offered when `CATTOMAIL_GLOBAL_OPTOUT_ENABLED`, with the server-checked "I understand" box, `confirm=yes`) creates a catto-mail global opt-out; it also unsubscribes the subscriber from all ctnlist lists. `POST /no-contact/withdraw` lifts it (`POST /v1/global-suppressions/{id}/lift`, idempotent, retried by the worker). Neither re-subscribes anyone, and the subscriber is told the real outcome (active, pending report, refused). Ordinary unsubscribes, including the one-click link and the banlist scopes, are never sent to catto-mail. `uq_cgo_open_per_subscriber` with `ON CONFLICT DO NOTHING` makes a double submit safe.

**Worker.** `CattoMailWorker` (`ctnlist:cattomail:work`, cron every minute; one at a time through `App\Maintenance\DatabaseLock`; exits 1 only on failures) processes unprocessed webhook events, unsealed jobs of finished or abandoned runs (no new job or accepted batch for an hour: a long run that is still staging is left alone), opt-outs and validation submissions, polls jobs without a final state older than `CATTOMAIL_RECONCILE_AFTER`, and asks for the sending domains while the From domain cannot send (counted, so printed, only on the pass that finds it ready: cron mails what it prints). `CattoMailActivity` keeps the last API success and error and the worker heartbeat in `options`; `App\Maintenance\StuckWork` defines stuck work (2 × the reconcile interval, at least 10 minutes) and the job categories.

**Administration.** `Admin\DeliveryController` (`logs.view`) and `Admin\AddressValidationController` (`subscribers.manage`). `/delivery` shows the mail service connection (with Connect, Disconnect and Forget for administrators), the configuration without secrets and a connection check (`CattoMailHealth` → `CattoMailClient::probe()`: `GET /v1/send-jobs/<PROBE_ID>`, where 404 means authenticated). Raw webhook bodies are never shown. Recovery actions are POST + CSRF and logged with the administrator's UUID; they only ask catto-mail again or repeat stored requests, and nothing sets a state by hand: retry an unsealed job (`queue.process`; refused while its run is staging or catto-mail is unconfigured), reprocess an unprocessed or failed event (`queue.process`), retry a validation submission or an opt-out (`subscribers.manage`). "Clear the sending block" on a subscriber page (`subscribers.manage`) clears the block only, never memberships or consent.

**Tests.** Integration tests use `tests/Support/FakeCattoMail`, a stateful fake of the `/v1` API at the HTTP boundary: auth, Idempotency-Key replay and conflict, batch and job limits, duplicates, unsubscribe rules, the opt-out capability, the connect flow (`approve()`/`decline()` stand in for catto-mail's connect page with its parameter rules; exchange, `DELETE /v1/connection` and `GET /v1/sending-domains` behave as the contract says, and a key issued by a connection is accepted until its connection ends), catto-mail's real problem types and fault injection (including "processed but response lost"); `finishOnRead` simulates an instant catto-mail. Call `IntegrationTestCase::fakeCattoMail()` before fetching any service that uses `CattoMailClient`. `tests/Integration/CattoMail/CattoMailTestCase` delivers signed webhooks through the HTTP kernel (`handle` + `terminate`). `ConnectFlowTest` clears the `CATTOMAIL_*` environment before booting the kernel, because the connection is used only for values `.env` leaves empty; build the configuration "as the next request would" with `CattoMailConfigFactory`, since the container's `CattoMailConfig` cannot be replaced once fetched.
